# Сверка взаиморасчётов по ОСВ и диагностика подключения

Только чтение. Всё ниже относится к бухгалтерской базе (`buh-ai`).

## 1. Почему запросы уходили в `zup-ai`, а бухгалтерских инструментов «не было»

Что установлено по исходникам (проверено чтением кода и истории git обоих проектов):

- Инструменты `read.accounting.*` (ОСВ и проводки документа) есть **только в ветке
  `megapolis/account-turnover` форка**. В опубликованном пакете `1c-odata-mcp@0.4.0` и в ветке
  `main` их нет. Сервер, собранный из npm, бухгалтерских инструментов не содержит.
- Инструментов с именами `get_accounting_balance` и `get_accounting_register` **нет и никогда не
  было** ни в этом сервере, ни в `@1c-odata/mcp`. Ответ `Tool … not found` на такие имена верен.
  ОСВ в этом сервере — `read.accounting.get_account_turnover`, проводки документа —
  `read.accounting.get_document_postings`.
- Инструментов произвольного OData-запроса в этом сервере **нет**. `query`, `register_query`,
  `get_entity`, `count` принадлежат другому пакету — `@1c-odata/mcp`.
- У обоих пакетов **одно имя исполняемого файла — `1c-odata-mcp`**. Какой из них запускается
  командой `1c-odata-mcp` или `npx 1c-odata-mcp`, зависит от того, что установлено на сервере.
- `@1c-odata/mcp` не читает `.env`: его подключения хранятся в собственном `config.json`
  (`1c-odata-mcp list`). Параметр `connection` у его инструментов обязателен.

Отсюда наиболее вероятная причина: клиент подключён к `@1c-odata/mcp`, в котором заведено
подключение к `zup-ai` и нет подключения к бухгалтерии. Тогда произвольные запросы идут в ЗУП, а
бухгалтерских инструментов нет вовсе.

**Это вывод из кода, а не наблюдение на сервере.** Конфигурация сервера MCP из среды разработки
недоступна. Подтверждается шагами раздела 3.

## 2. Что изменено в ОСВ

`read.accounting.get_account_turnover` получил три необязательных параметра:

| Параметр | Что делает |
|---|---|
| `counterpartyRef` | Ref_Key контрагента: в ведомости остаётся только его аналитика |
| `contractRef` | Ref_Key договора: только этот договор |
| `breakdown: "contract"` | добавляет массив `contracts`: итог и субсчета по каждому договору, строки без договора — отдельной группой |

Сальдо остаётся развёрнутым: Дт и Кт суммируются раздельно по строкам «Остатков и оборотов»
(счёт × измерения × все субконто, включая документ расчётов), в том числе внутри договора. Долг
по одному документу не сворачивается с авансом по другому.

Отбор уходит в `$filter` 1С. Если база отвечает на него 400, запрос повторяется без отбора, а
строки отбираются на стороне сервера; какой путь сработал, показывает поле `dimensionFilter`
(`server` или `client`). Несуществующий Ref_Key — ошибка, а не ведомость из нулей.

Пример: расчёты клиники с ИП по счёту 60 за январь 2025.

```json
{
  "organization": "<часть названия клиники>",
  "account": "60",
  "from": "2025-01-01",
  "to": "2025-01-31",
  "counterpartyRef": "<Ref_Key ИП в справочнике контрагентов>",
  "breakdown": "contract"
}
```

В ответе `accounts` содержит `60.01` и `60.02` с начальным сальдо, оборотами и конечным сальдо.
Для стороны ИП — то же с `"account": "62"`, организацией ИП и контрагентом-клиникой.

## 3. Развёртывание и проверка на сервере MCP

На сервере нет ручных клонирований и сборок: образ собирает Docker из репозитория развёртывания
`mc-mcp-deploy`, в котором версия этого модуля закреплена git-ссылкой на коммит. Пошаговая
инструкция — в README репозитория развёртывания. Здесь только то, что относится к модулю.

Модуль ставится в образ зависимостью:

```json
{ "dependencies": { "1c-odata-mcp": "git+https://github.com/AlexMarinenko/1c-odata-mcp.git#<коммит>" } }
```

В образе доступны два исполняемых файла:

| Команда | Назначение |
|---|---|
| `1c-odata-mcp` | сервер MCP (stdio) |
| `1c-odata-mcp-settlements` | диагностика и сверка взаиморасчётов, только чтение |

Диагностика (адреса без учётных данных, имена инструментов, структура строки ОСВ):

```bash
docker run --rm --env-file /etc/mc-mcp/buh.env mc-mcp-buh:<версия> 1c-odata-mcp-settlements
```

В выводе проверьте:

- шаг 1 — адрес базы оканчивается на `/buh-ai/odata/standard.odata/`, вывод «бухгалтерская база»;
- шаг 2 — «отбор по контрагенту и договору: есть»;
- шаг 3 — «шесть ресурсов: есть», «поля типа субконто: есть»;
- шаг 4 — как в базе названы организации.

Проверка за январь 2025 (названия подставьте из шага 4 и справочника контрагентов):

```bash
docker run --rm --env-file /etc/mc-mcp/buh.env mc-mcp-buh:<версия> 1c-odata-mcp-settlements \
  --org-a "<клиника>" --cp-in-a "<ИП как контрагент>" \
  --org-b "<ИП>" --cp-in-b "<клиника как контрагент>" \
  --from 2025-01-01 --to 2025-01-31
```

Весь период по месяцам — те же аргументы с `--from 2025-01-01 --to 2026-06-30 --monthly`.

Сторона A — организация, у которой вторая сторона поставщик (счёт 60); сторона B — организация,
у которой первая сторона покупатель (счёт 62). Если ИП не ведётся организацией в этой базе,
уберите `--org-b` и `--cp-in-b`: будет показана только сторона клиники.

Если по названию находится несколько контрагентов, команда перечислит их с Ref_Key; повторите
запуск, указав нужный Ref_Key вместо названия.

## 4. Что проверено и что нет

Проверено: 197 автотестов (17 новых на отбор и разбивку), линтер, форматирование, сборка;
команда сверки выполнена целиком против локальной имитации OData по HTTP, включая ветку с
ответом 400; установка пакета по git-ссылке на коммит (сборка через `prepare`, оба исполняемых
файла на месте, probe-скрипты в пакет не попали).

**Не проверено на живой базе** (из среды разработки она недоступна):

- принимает ли 1С `$filter` по субконто виртуальной таблицы через `cast`. Если нет, сработает
  отбор на стороне сервера, и в ответе будет `dimensionFilter: "client"`;
- отдаёт ли база поля `ExtDimensionN_Type` в строках «Остатков и оборотов». Без них отбор по
  контрагенту работает (сравнение по GUID), а разбивка по договорам вернёт явную ошибку;
- ведётся ли ИП отдельной организацией в `buh-ai`.

Развёрнутое сальдо двух сторон может не совпадать зеркально, даже если расчёты сходятся: стороны
по-разному разносят оплаты по документам. Поэтому скрипт дополнительно сравнивает свёрнутое
конечное сальдо.
